## 1. 项目概述

牙齿矫正综合类平台，包含一个接口服务和三个前端（doctor 延后启动）：

| 端 | 目录 | 技术栈 | 使用者 | 说明 |
|---|---|---|---|---|
| 小程序（患者/医生共用） | `app/` | UniApp（Vue3） | 患者、医生 | 同一小程序按角色区分：患者功能 + 医生日常操作（患者管理、打卡跟踪、资讯发布等）；目前仅微信小程序，后续同一套代码扩展 Android / iOS |
| 平台管理后台 | `backend/` | Vue3 + Ant Design Vue | 平台工作人员 | 内容审核、机构/医生/产品管理、运营配置 |
| 医生端网页后台 | `doctor/` | Vue3 + Ant Design Vue | 医生 | **项目保留、延后启动**：日常操作走小程序，此端专用于后期复杂排牙计划（排牙方案设计与调整）等网页端操作 |
| 后台接口服务 | `api/` | ASP.NET Core 10（net10.0）+ FreeSql + PostgreSQL + Redis | — | 纯 Web API 无 UI；定时任务使用 FreeScheduler |

外部系统（本期只做对接边界，不实现内部逻辑）：

- **AI 专业系统**（外部）：AI 模拟与专业分析报告由专业人员训练，本平台**预留接口**。
- **第三方商城系统**（外部）：商城由第三方支持，本平台只**拉取商品列表展示**。
- **微信开放能力**：小程序登录（jscode2session，已有雏形）、订阅消息（打卡/更换提醒）。

## 2. 总体架构

```
患者/医生小程序(app)   平台后台(backend)   医生端网页(doctor)
        \             |               /
         \  HTTPS：统一 REST API（Response<T> 包裹 + 请求签名 + Redis 会话）
          ▼
   api 接口服务（ASP.NET Core 10 + FreeSql + PostgreSQL + Redis + FreeScheduler）
          |                        |
          ▼                        ▼
   AI 专业系统（回调预留）    第三方商城（商品拉取）
```

### 2.1 开发约定（摘自 CLAUDE.md，全期遵守）

1. `Admin.Models` 新增实体后，必须同步在 `SystemService.InitSystemAsync()` 增加 `_fsql.CodeFirst.SyncStructure<T>()` 及默认数据。
2. 建表时根据字段业务属性（查询、排序、唯一性）用 `FreeSql.DataAnnotations.IndexAttribute` 加索引。
3. 三个前端全部走 i18n：**简体中文（默认）+ 英语**；api 用户可见文案通过 `Resources` 本地化。
4. API 统一 `Response<T>{code,msg,data}`；错误抛 `CodeException`；请求签名与会话机制沿用 `AdminCheck` / `AppCheck`。
5. 实体命名沿用现有风格：小写属性、`created_at/updated_at/deleted_at` 为 Unix 秒（long）、软删除。
6. 提醒、商城商品同步等定时任务统一用 FreeScheduler。

## 4. 数据模型规划（主要表）

实体统一放 `Admin.Models`，遵循第 2.1 节约定。已有的 `user`、`account/role/module`、`corp/corp_department/corp_account`（模型已存在，初始化被注释）优先启用复用。

**账号设计决策【已确认】：认证身份合一，角色差异下沉到档案表。**

- **医生与患者共用 `user` 账号表**：两者都走微信小程序登录，身份锚点是 `openid`/`unionid`（唯一索引保证一个微信人一行）。`user` 新增 `role` 列（新枚举 `UserRole`：Patient / Doctor）；现有 `type`（Client / WechatMP）语义为注册渠道，保留不动。
- **`doctor` 为 `user` 的 1:1 档案扩展表**：`user_id` 唯一关联，存放姓名、职称、专长、简介等医生专属信息，以及平台认证状态（待审 / 通过 / 驳回）；不承担登录职责。`doctor_case`、`doctor_corp` 挂 `doctor_id`。
- **权限判定**：医生工作台 = session 中 `role == Doctor` 且 `doctor` 档案已通过认证。
- **边界**：医生本人也是患者（戴牙套/购物）天然支持——同一行账号既有档案又可用患者功能，也为将来"一个账号多角色"留了演进空间；平台后台人员走 `account`，机构内身份复用 `corp_account`，均不并入 `user`。

| 模块 | 表 | 用途 |
|---|---|---|
| 账号 | `user`（新增 `role` 列）、`doctor`（档案） | 患者与医生共用账号表；医生档案（1:1 扩展，含认证状态） |
| 基础 | `corp`（扩展）、`corp_photo`、`corp_review` | 机构信息、环境相册、用户评价 |
| 找医生 | `doctor_case`、`doctor_corp` | 医生案例、执业机构关联（挂在 `doctor` 档案下） |
| 找产品 | `brand`、`product`、`product_ref` | 供应商品牌、产品、产品—医生/机构关联展示 |
| 牙套打卡 | `aligner_plan`、`checkin_record`、`wear_stat` | 矫治计划（牙套副数/日程）、摘戴打卡、时长/连续性/规律性统计与评分 |
| 复诊跟踪 | `replace_plan`、`replace_record` | 更换周期（默认 14 天、医生可自定义）、更换记录+口内照 |
| 资讯/积分 | `post`、`post_media`、`comment`、`follow`、`points_account`、`points_ledger` | 帖子（图文/视频+文字）、评论、关注、积分账户（医生/患者区分 owner_type）、积分流水 |
| 商城 | `mall_product`、`cart_item` | 第三方商品同步缓存、购物车 |
| 首页 | `banner`、`news` | 优惠活动、新闻动态 |
| AI 预留 | `ai_task`、`ai_material`、`ai_report` | 统一任务模型：素材、任务状态、报告存储 |

> 详细字段设计在各阶段开发前出表设计稿评审后再落码。

## 5. 外部系统对接设计

### 5.1 AI（模块 1、2 —— 均为预留接口）

统一"AI 任务"模型，本期保证链路可空跑（mock 实现）：

```
用户上传素材 → 创建 ai_task(pending) → 推送/暴露给 AI 专业系统
→ 外部回调写入结果（签名鉴权）→ task=done → 小程序展示
```

- **模块 1 用户 AI 自测**：拍照/上传 → 提交矫正模拟或贴面模拟任务 → 前后两张照片对比展示。接口：提交任务、查询任务、获取结果图。
- **模块 2 专业 AI 方案**：批量上传面相照、口内照、CBCT、侧位片、牙齿 3D 模型 → 生成专业分析任务 → 展示分析报告（AI 或人工产出均走同一报告模型）。复杂排牙计划的 doctor 网页端操作为后期专项（见第 6 节）。
- 对外提供回调接口，沿用签名鉴权；素材规格与回调协议需与 AI 团队约定（见待确认问题）。

### 5.2 第三方商城（模块 5）

- FreeScheduler 定时任务拉取第三方商品列表 → 写入 `mall_product` 缓存表；后台可手动触发同步。
- 小程序只读展示商品列表/详情，购买跳转第三方商城（购物车归属、是否二次跳转支付，见待确认问题）。

### 5.3 微信订阅消息

- 申请"牙套更换提醒""复诊提醒"模板；FreeScheduler 扫描 `replace_plan` 到期数据并推送。
- 打卡连续中断提醒可作为二期增强。

### 5.4 文件存储（本地存储 + 签名地址直传/下载）【已确认】

存储先用本地磁盘，但接口按**预签名**语义设计，未来可平滑切换 OSS：

- **上传**：客户端先调接口申请签名上传地址（携带文件名/类型/大小/业务场景）→ 获得 `upload_url` + `file_key` → 向 `upload_url` **直传**文件 → 业务侧只落库 `file_key`。
- **下载**：客户端申请签名下载地址（或业务接口直接返回带签名的 `download_url`）→ **时效内**可下载，过期失效。
- **实现**：api 提供签发接口；上传/下载端点用 HMAC（复用 `EncryptorService` 密钥体系）校验签名与有效期后读写本地磁盘。切换 OSS 时仅替换读写实现为 OSS 预签名，接口语义不变，前端无需改造。
- 待开发中确定的小参数：签名有效期时长、单文件大小上限、大文件（CBCT/3D 模型）是否需要分片。

## 6. 分期开发计划

### 阶段 0：基础设施与账号体系

**目标**：api / backend / app 脚手架可运行、可登录、可部署（doctor 延后）；权限与机构模型就绪。

- **api**（新版脚手架已就绪：`Admin.Api` 纯 Web API，net10.0，控制器/过滤器/DI/本地化均已启用）
  - 启用并完善 `corp` 系列实体；按第 4 节账号设计落地：`user` 新增 `role` 列（患者/医生共用账号表）、新建 `doctor` 档案表（含认证状态）；区分后台人员 / 医生 / 患者三类角色，医生可登录小程序进入医生工作台。
  - 微信小程序登录联调（`wx-mp-login` 已有雏形；顺手修复 `AppCheckAttribute` 误用 `AdminSessionService` 校验会话的问题，应为 `AppSessionService`）。
  - 文件签名直传/下载服务（本地存储 + 预签名接口，见 5.4）。
  - 默认请求文化改为 zh-Hans（当前 `Program.cs` 默认 en-US，与"默认简体中文"需求不符）；`Resources` 资源补全中英两种语言。
- **backend**：Vue3 + Vite + TS + Pinia + Vue Router + vue-i18n + Ant Design Vue 脚手架；登录、布局、菜单权限（对接 module/role）；请求封装（签名/会话头）。
- **app**：UniApp（Vue3）脚手架；微信登录（区分患者/医生角色，医生登录后进入医生工作台）；i18n；请求封装（App 会话 + 签名）。
- **docker**：nginx 增加 backend 静态站点与 api 反代配置（doctor 站点待排牙专项启动时补充）；核对 dockerfile 产物名（`Admin.Api`）。
- **交付物**：api / backend / app 空壳可登录（患者、医生角色）；部署脚本更新。

### 阶段 1：找机构 / 找医生 / 找产品 + 首页框架

**目标**：小程序内容骨架可用，后台可维护基础数据。

- **api**：机构（资质/地点/环境/服务/评价）、医生（简介/案例/所属机构）、产品（品牌/关联医生与机构）的 CRUD 与查询接口；评价接口；首页聚合接口（banner、news、各模块入口）。
- **backend**：机构/医生/品牌/产品管理页；banner、新闻管理；评价审核。
- **app**：找机构（大众点评式详情页）、找医生、找产品列表与详情；首页框架（打卡入口占位、更换提醒占位、优惠活动、新闻动态、关注动态占位、购物车与我的入口占位）。
- **交付物**：小程序可浏览机构/医生/产品；后台可维护。

### 阶段 2：牙套打卡 + 复诊跟踪

**目标**：患者核心闭环上线，医生可在小程序内跟踪。

- **api**：`aligner_plan` 矫治计划管理；摘/戴打卡接口；佩戴时长、连续天数、规律性统计与评分（评分细则需产品确认，先实现可配置规则）；`replace_plan` 更换周期（默认 14 天、医生可改）；更换记录+口内照上传；FreeScheduler 提醒任务 + 订阅消息推送。
- **app（患者）**：打卡页（摘/戴一键打卡）、打卡日历与统计展示、评分与更换提醒展示、复诊跟踪页（更换拍照上传）、**口内拍照神器购买入口**（跳转商城模块）。
- **app（医生角色）**：患者列表、打卡数据看板（时长/连续性/规律性/评分）、更换计划调整。
- **backend**：打卡/复诊数据统计报表。
- **依赖**：微信订阅消息模板申请通过。

### 阶段 3：资讯发布与浏览 + 积分

**目标**：类小红书内容社区上线，积分账本就绪（用途预留）。

- **api**：帖子发布（图片/视频 + 文字）、浏览/信息流、评论、关注（医生↔患者互关）；积分规则（发布文字得积分）与 `points_account/points_ledger` 账本（医生/患者区分，作用后续备用）；首页"关注动态"聚合。
- **app（医生角色）**：医生在小程序内发布/浏览资讯、查看粉丝与评论。
- **backend**：工作人员发布入口、内容审核（先发后审/先审后发待确认）。
- **app（患者）**：资讯信息流、详情、发布、评论、关注页。
- **依赖**：阶段 0 的文件签名直传服务就绪（图片/视频走 5.4 设计）。

### 阶段 4：美牙产品商城对接（依赖第三方就绪）

**目标**：商品展示与购买跳转可用。

- **api**：第三方商城商品拉取与定时同步（FreeScheduler）、商品列表/详情接口、购物车接口。
- **backend**：同步配置（手动触发、同步日志）。
- **app**：商品列表/详情、购物车、"我的"完善；阶段 2 的拍照神器入口落地到此。
- **依赖**：第三方商城 API 文档与联调账号（**外部依赖，需提前启动商务对接**）。

### 阶段 5：AI 接口预留与联调（依赖 AI 团队协议）

**目标**：模块 1、2 的"上传—任务—回调—展示"链路可演示（AI 结果可用 mock 图/报告）。

- **api**：`ai_task/ai_material/ai_report` 落库；小程序任务提交/状态查询/结果获取接口；对 AI 专业系统的任务推送与回调接口（签名鉴权）；大文件（CBCT/3D 模型）走 5.4 签名直传通道，必要时评估分片上传。
- **app（患者）**：AI 自测页（拍照/上传、前后对比展示）、专业方案页（素材上传、报告展示）。
- **app（医生角色）**：医生查看与管理自己患者的方案任务与报告。
- **backend**：方案任务列表、报告查看、人工出报告的录入入口（模块 2 支持人工）。
- **依赖**：与 AI 团队确认回调协议、素材规格。

### 后期专项：doctor 网页端复杂排牙计划（暂不排期）

doctor 项目保留但延后启动，日常医生操作均在小程序内完成。doctor 网页端专用于复杂排牙计划（如基于牙齿 3D 模型的排牙方案设计、调整与确认），待 AI 排牙能力与协议明确后单独立项，届时补充脚手架（与 backend 同栈：Vue3 + Ant Design Vue）、表设计与接口。

## 7. 风险与待确认问题

**已确认**：
- 文件存储：本地磁盘 + 签名地址直传/下载（见 5.4）。
- api 脚手架：新版 `Admin.Api`（net10.0 纯 Web API，无 Blazor）。
- 账号体系：医生/患者共用 `user` 账号表（`role` 列区分），`doctor` 为 1:1 档案扩展表（见第 4 节）。

**暂未确定**（2026-09-07 确认，不阻塞阶段 0–2 开发，到达对应阶段前需落定）：

1. **第三方商城**：具体商城系统、API 能力范围、购物车归属（平台侧 or 商城侧）、支付是否在小程序内闭环。
2. **微信合规**：订阅消息模板申请、小程序"医疗健康"类目及资质、内容与活动文案的医疗广告合规。
3. **AI 对接协议**：回调鉴权方式、素材规格（照片拍摄要求、CBCT 导出格式、3D 模型文件格式）、任务时效。
4. **积分规则**：医生/患者积分是否分账分规则、发放细则、防刷机制。
5. **内容审核流程**：先发后审还是先审后发；评价是否可匿名。
6. **多租户粒度**：医生相关数据按机构隔离（复用 `corp_account`），连锁机构多院区是否需要 `corp_department` 启用。
7. **提醒策略**：更换提醒的触发时间点、免打扰时段、患者关闭提醒的处理。
