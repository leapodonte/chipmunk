# 开发 Roadmap V2.0（按现有技术栈）

版本：V2.0，取代 V1.0
日期：2026-09-08
配套：`10_现有实现评审.md`（阶段 0 的修复清单来源）、`开发计划1.0.md`（模块清单与阶段划分的来源）、`09_设计文档与实现现状对照.md`（两套文档的边界）、`CLAUDE.md`（工程约定）

## 0. 这版改了什么

V1.0 写于本仓库建立之前，假设的是 EF Core、Hangfire、Element Plus、阿里云 OSS，和一套自定义的 M0 到 M4 里程碑。这些与本仓库全部不符。

V2.0 按仓库现状重写：

| 项 | V1.0 | V2.0 |
| --- | --- | --- |
| 阶段划分 | M0 到 M4 | 沿用 `开发计划1.0.md` 的阶段 0 到 5，加一个阶段 2B |
| 后端 | ASP.NET Core 加 EF Core 加 Hangfire | ASP.NET Core net10.0 加 FreeSql 加 FreeScheduler |
| 后台前端 | Element Plus，一个后台 | Ant Design Vue，`backend/` 与 `doctor/` 两个 |
| 主键与时间 | ULID、TIMESTAMPTZ | Guid、Unix 秒 |
| 文件 | OSS 双桶加 CDN | 本地磁盘加预签名接口，接口语义兼容将来切 OSS |
| 建表 | 手写 SQL | FreeSql 实体 CodeFirst |
| 起点 | 从零建仓库 | 先修复现有脚手架的阻塞缺陷，再加业务 |

保留了 V1.0 里仍然成立的部分：外部系统清单与降级策略、日历硬约束、团队节奏、灰度顺序。

**新增一个阶段 2B「保持器订单」。** 9 月 6 日会议定的第一条现金流是透明保持器，但 `开发计划1.0.md` 的九个模块里没有订单与供应链。这个缺口必须补，否则年底上线的是一个不能收钱的平台。放在阶段 2 之后，是因为它依赖阶段 2 的医患关系与阶段 0 的文件服务。

## 1. 技术栈基线

以下就是现在仓库里的东西，不再讨论替换。

| 层 | 选型 | 备注 |
| --- | --- | --- |
| 接口 | ASP.NET Core net10.0，`api/Admin.sln` 三项目 | 路由 `admin/[controller]`、`app/[controller]`，无 `/api` 前缀 |

| 缓存 | FreeRedis 1.5.5 | 会话、微信 token、以后的 nonce 与限流 |
| 定时任务 | FreeScheduler | 尚未引入，阶段 0 加 |
| 日志 | log4net 3.3.2 | 阶段 0 做脱敏与级别调整 |

## 3. 阶段 0：修复与骨架（09-09 → 10-06）

### 3.1 入口条件

无。这是当前状态。

### 3.2 前置修复，任何新表落地前完成

来自 `10_现有实现评审.md` §3 的 P0 清单，合计约 3.5 天，必须先做：

| # | 事项 | 为什么不能拖 |
| --- | --- | --- |
| 1 | `user` 索引字段名 `open_id` 改 `openid`、`unique_id` 改 `unionid`；`--init` 加索引自检 | 不修则只能注册一个用户 |
| 2 | `AppCheck` 换 `AppSessionService`，加 `GetAppSession()` | 不修则小程序无法调任何需登录接口 |
| 3 | 两处登录的 `updated_at` 更新补 `Where` | 全表写 |
| 4 | `--init` 拆成 `--sync` 与 `--seed`，admin 只插不覆盖 | 后续每加表都要跑，不能重置密码 |
| 5 | 软删除定调：建议真做，用 FreeSql 全局过滤器 | 新表要照约定写，约定得先成立 |
| 6 | `admin/corp/get` 与 `admin/auth/current-user-roles` 补路由 | 前端联调会 404 |
| 7 | 微信 token 缓存三处错、证书校验、`IHttpClientFactory` | 阶段 2 推送会触发频控，证书是安全问题 |
| 8 | 资源键 `InvalidStream` 与拼写清理 | 错误文案 |
| 9 | 示例配置的 Redis 空格与库名 | 新人照抄会连不上 |

### 3.3 账号与角色

按 `开发计划1.0.md` 第 4 节已确认的设计：

- `user` 加 `role` 列，`UserRole { Patient, Doctor }`；`type` 保持为注册渠道。
- 新建 `doctor` 实体：`user_id` 唯一，姓名、职称、专长、简介、认证状态、审核人、审核时间。
- `AppSession` 改为存 `user_id`、`role`、`doctor_verified`，不存整个实体。
- `corp`、`corp_department`、`corp_account` 取消注释纳入 `--sync`，先修 `CorpAccount` 的可空标注。
- 医生工作台判定：`role == Doctor` 且档案已通过认证。

**疗程的决策在这里做。** `09_设计文档与实现现状对照.md` §4.2 说明了为什么没有疗程概念会让阶段 2 的归属查询写不出来。建议在阶段 0 就定：新增 `course` 表，`patient_user_id`、`doctor_user_id`、`corp_id`、`status`、`source`、起止时间，唯一约束「同一患者同一医生同时只有一条进行中」。阶段 2 的 `aligner_plan`、`replace_plan` 都挂 `course_id`。

### 3.4 文件服务

按 `开发计划1.0.md` 5.4：

- `app/file/upload-policy`：传业务类型、扩展名、大小，返回 `upload_url`、`file_key`、过期时间。
- `app/file/upload`：校验签名与有效期后写本地磁盘 `Storage:Root/{biz}/{yyyyMM}/{guid}.{ext}`。
- `app/file/sign-url`：返回带签名的下载地址，默认 10 分钟。
- 新增 `file_object` 实体登记每个文件：`file_key` 唯一、业务类型、业务 id、大小、MIME、状态。理由见对照文档 4.4，切 OSS 与清孤儿都要用。
- nginx 的 `/storage/` 反代指向这组接口。

### 3.5 横切能力

- 引入 FreeScheduler，注册一个空的心跳任务验证运行。
- `MapHealthChecks("/healthz")` 检查 PG 与 Redis。
- `AddOpenApi()`，开发环境暴露 `/openapi/v1.json`。
- 默认文化改 zh-Hans。
- 密钥移入配置，生产用环境变量。
- 签名 nonce 去重，容差收窄到 5 分钟。
- 日志脱敏，`CodeException` 记 Warn。
- RBAC 服务端强制：`[RequireModule]` 特性。

### 3.6 三端骨架

- `app/`：按 `05_M0详细设计.md` §8.5 的迁移清单把前身仓库代码搬入，改请求封装适配 `App-RequestId` 头与 ±5 分钟容差；tab 从四项改五项；登录后按 `role` 分流。

- `docker/`：重写 `web.conf`，去掉 9998、WebSocket、MQTT；`dockerfile` 改多阶段构建；补 `db` 与 `redis` 的示例 compose。

## 5. 阶段 2：牙套打卡与复诊跟踪（10-28 → 11-24）

### 5.1 接口

- `aligner_plan`：挂 `course_id`，副数、每副天数（默认 14）、开始日期。
- `checkin_record`：摘或戴、时间；一键打卡按上一条状态自动判定。
- `wear_stat`：每日结算总时长、连续性、均衡性，权重 6、3、1 可配置。FreeScheduler 每日凌晨结算。
- `replace_plan`、`replace_record`：换套到期、提前一天与当天提醒、换套拍照上传走文件服务。
- 微信订阅消息：换套提醒、打卡提醒，授权在打卡页收集。
- 医生端接口：我的患者（按 `course`）、患者打卡看板、调整换套周期。

### 5.2 前端

- 小程序患者：打卡页、日历与统计、换套任务、拍照上传。
- 小程序医生：患者列表、看板、周期调整。
- 后台：打卡与复诊统计报表。

### 5.3 依赖

订阅消息模板必须在此前申请通过。超月在阶段 0 启动。

### 5.4 退出标准

## 6. 阶段 2B：保持器订单（11-25 → 12-15）

### 6.1 为什么加这个阶段

9 月 6 日会议：保持器是第一现金流，从存量正畸结束用户切入。`开发计划1.0.md` 没有订单模块。没有它，年底上线的平台不能收钱。

### 6.2 最小闭环

只做把一笔订单从登记走到签收的最短路径，不做支付闭环，定金线下收。

- `retainer_order`：挂 `course_id`，状态机 `待口扫 → 待设计 → 设计中 → 待确认 → 生产中 → 已发货 → 已签收`，口扫文件 key、供应商单号、物流单号。
- `app/order/create`（医生发起）、`app/order/list`、`app/order/detail`（医患都可看）。
- 供应商设计：签发一次性 token，`web-view` 整页打开供应商系统；`open/supplier/webhook` 接收设计完成、生产、发货事件，验签与幂等。接口协议按 `05_M0详细设计.md` §7.3。
- 物流：先手工录入单号，快递查询接口放阶段 4。
- 后台：订单列表、状态人工修正、供应商配置。

### 6.3 依赖

供应商接入方式与计费口径，杨老师侧商务在阶段 1 内谈定。谈不定则 webhook 换成后台人工改状态，闭环仍然成立。

### 6.4 退出标准

一笔真实保持器订单在系统内走完全部状态，医患两端都能看到进展。

## 14. 风险

| 风险 | 影响 | 对策 |
