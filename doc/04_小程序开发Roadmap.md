## 2. M1 平台骨架（09-22 → 10-18）

小程序
- 登录：微信静默登录 + 手机号验证码；协议勾选；游客态。
- 角色：patient / doctor 渲染分流；分包结构落地。
- 偏好问卷：注册流程中的十几题；结果写入用户画像。
- 疗程与绑定：医生二维码（带 scene 的小程序码）→ 扫码落地 → 创建疗程；无医生浏览态；选择医生。
- 发现流骨架：帖子列表、详情、发布（图文）、医生主页、基础过滤。
- 我的：资料、疗程与医生、报告与模拟记录入口、设置与协议。
- 自测模块迁移：复用现有页面，弱化评分展示。

后端
- 身份与关系、内容、配置与运营三个域的表与接口。
- AI 任务编排域：复用现有 analysis 任务模式，接入插件注册表。
- 运营后台最小版：用户/医生管理、医生认证、内容审核、协议与配置。

插件接入
- P1 AI 正面排齐模拟：LEO 将现成模型部署为 SaaS，提供任务 API；zsj 接入上传直传、任务创建、结果轮询、结果页。
- P2 拍摄姿态检测：沿用现有端侧能力，作为上传前的可选引导。
- C 类：对象存储直传、短信、微信登录与小程序码。

验收：医生可生成二维码，患者扫码进入完成问卷并绑定；可发帖、可浏览；可完成一次 AI 模拟并看到前后对比。

## 3. M2 依从性与沟通（10-19 → 11-15）

小程序
- 打卡：底部中央加号、一键戴/摘、周期与副数设置、三指标评分图表、历史记录。
- 复诊监控：换套倒计时、前一天与当天提醒、换套拍照上传、时间轴。
- 消息中心：私信 1:1、评论与关注通知、系统通知、未读角标。
- 视频：帖子支持视频上传（直传 + 转码回调）与播放。
- 商城入口：有赞 H5 整页承载或跳转，订单在「我的」展示。

后端
- 依从性域：事件、周期、评分结算定时任务、换套计划与提醒任务。
- 消息域：会话、消息、未读、订阅消息投递与授权记录。
- 商城适配域：有赞订单 webhook 映射。
- 内容域：视频媒体、转码状态、审核流程。

插件接入
- P7 商城（有赞类 SaaS）：账号开通、H5 接入、订单回传。
- P8 视频存储分发：OSS + CDN + 转码，鉴权 URL。
- P9 微信订阅消息：模板申请与投递；站内推送策略。
- P12 大模型文案（DeepSeek 等，可选）：科普摘要、报告文案，经合规过滤。

验收：患者连续打卡并看到评分；换套提醒准时到达并能上传照片；医患可私信并收到微信通知；可在商城下单并在小程序看到订单。

## 4. M3 交易与供应链 + 内测（11-16 → 12-13）

小程序
- 保持器订单：需求登记、订单详情、状态与物流、复购提醒。
- 医生端：我的患者列表与筛选、疗程内打卡/换套看板、方案发起入口（跳转供应商）、发布案例模板、集中回复私信。
- 增长：患者邀请码（挂靠医生）、积分账户与流水、基础奖励展示。
- 找医生：列表、筛选、主页完善。

后端
- 订单与供应链域：订单状态机、设计任务、生产状态、发货与物流同步、复购提醒任务。
- 增长与积分域：两层裂变校验、积分规则引擎（可配置）、医生积分统计。
- `/open` webhook：供应商方案与生产状态回传、物流回传、幂等与签名。

插件接入
- P5 供应商牙套/保持器设计：一次性 token 单点登录、web-view/桌面跳转、方案与状态回传；计费按次记录。
- P6 口扫处理/封牙模块（LEO 自研）：先作为内部服务承接口扫建档与预处理，为后续替换供应商环节做准备。
- P13 物流查询：拉取 + 回传。
- P11 内容安全：UGC 文本与图片机审。

内测
- 医生先进：首批医生认证、各自建案例，目标累计 100–1000 个案例。
- 运营灌入官方科普内容。
- 每周收集医生反馈，PM 归入需求池。

验收：一笔保持器订单从登记到物流签收在系统内完整可见；医生能在小程序完成拉新、看板、发案例、发起设计、回复私信。

## 5. M4 灰度上线（12-14 → 12-31）

- 医生邀请患者（每位约 10 人），观察绑定、打卡、私信、模拟的真实数据。
- 合规文案包全部上线：协议、授权、AI 免责、未成年人提示、禁用词自检。
- 性能与稳定：信息流分页与缓存、任务队列压测、错误监控、告警。
- 微信审核：类目资质、隐私协议、订阅消息模板、业务域名。
- 正式发布并保留灰度开关（按医生白名单放量）。

验收：灰度用户核心链路无阻断性问题；监控与告警可用；PM 出上线报告。

## 9. 开发流程规范

- AI 辅助开发：方案与评审用最强模型（LEO 用 Claude 出详细评审与设计），实现用 GLM/其他模型（zsj）；方案文档先行，再实现。
- 代码流程：功能分支 → PR → LEO 或 zsj 交叉评审 → 合并；架构决策写入仓库 `docs/decisions`。
- 文档：产品说明与用户故事在飞书；接口文档随代码维护；数据字典变更需评审。
- 测试：核心链路（登录、绑定、打卡、私信、订单）有自动化用例；每个里程碑做一次真机回归（微信开发者工具 + 真机）。
- 环境：dev 自测、test 体验版给 PM 与杨老师、prod 灰度。
- 会议：周会看板过一遍阻塞；月会向杨老师演示可用功能并确认下月范围。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 公司主体、支付、类目资质晚到 | 无法正式发布与收款 | M0 即提交；体验版不受影响；灰度可先不开支付 |
| 供应商设计软件接入谈不下来或接口不齐 | 保持器链路断在设计环节 | 先跳转 + 人工回传；P6 自研模块作为后备 |
| 两名开发承载全量骨架 | 里程碑延期 | 每模块只做粗版；非核心（找机构、找产品、套餐）明确推到第二步；设计稿提前一个里程碑交付 |
| 微信审核（医疗类目、UGC） | 上线被拒 | 合规文案提前自检；先审后发；准备资质材料 |
| AI 模拟效果不稳定 | 引流口碑受损 | 免责文案；失败重试；LEO 用口扫数据持续训练 |
| 内容空壳 | 上线留存差 | 内容团队 M2 起灌入；医生案例作为内测目标 |
| 私信实时性 | 体验差 | 轮询 + 订阅消息起步；数据量上来后再评估 IM |
| 签名密钥在客户端 | 接口被滥用 | 会话令牌 + 限流 + 关键操作二次校验（2027 Q1 技术债） |
