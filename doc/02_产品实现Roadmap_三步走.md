# 牙套之家（暂名）· 产品实现 Roadmap（三步走）

日期：2026-09-08
依据：09-06 会议确定的三阶段（保持器 → 保持器+微调 → 正畸平台）、09-02 杨老师的完整平台构想、07 月计划书的阶段划分、LEO 关于「年底功能粗版并局部上线」的承诺。
原则：每一步都必须闭环一条能收钱的业务线；平台骨架在第一步一次搭全，后续步骤只加模块不改架构；关键技术以插件方式接入，先用现成再逐个替换。

---

## 0. 总览

| 步骤 | 时间 | 业务主线 | 产品目标 | 退出标准 |
| --- | --- | --- | --- | --- |
| 第一步：骨架 + 保持器切入 | 2026-09 → 2027-03 | 透明保持器（存量正畸结束用户，通过现有医生） | 小程序全量功能骨架上线；医生拉新 → 患者打卡 → 保持器订单跑通 | 年底局部灰度；首批医生入驻并各建案例；保持器订单全链路（口扫→设计→生产→物流）真实跑通 |
| 第二步：保持器 + 微调 | 2027-04 → 2027-12 | 轻微反弹微调（3–15 副）+ 保持器售后与产能爬坡 + 服务套餐 | 方案设计与专家审核流程成熟；复诊监控 AI 化；医生网页端；内容与推荐形成飞轮 | 微调订单稳定；套餐可售；月活达到阶段目标；供应商链路可替换 |
| 第三步：正畸平台 | 2028 起 | 隐形矫治全流程（200 元/副，自有 OEM）+ 四端协同 + 下沉市场推广 | 找医生/找机构/找产品与广告位商业化；自研设计模块替换供应商；App 版本 | 隐形矫治成为主要收入；平台在目标城市形成医生网络 |

对应 07 月计划书：第一步覆盖计划书阶段 0–2，第二步覆盖阶段 3–4，第三步对应阶段 5。

## 1. 第一步：平台骨架 + 保持器切入（2026-09 → 2027-03）

### 1.1 目标

- 一个微信小程序承载患者与医生两种角色，功能范围「全量骨架、粗版可用」。
- 以现有正畸结束的存量用户为对象，通过医生二维码进入，打卡、内容、私信留住，保持器订单变现。
- 年底（2026-12）局部灰度上线，2027 Q1 完成第一轮真实订单验证。

### 1.2 产品范围

| 模块 | 第一步交付内容 | 备注 |
| --- | --- | --- |
| 注册与登录 | 微信静默登录 + 手机号验证码；注册偏好问卷 | 公司主体认证后评估微信一键手机号 |
| 医患关系 | 医生二维码绑定、疗程创建、无医生浏览态、选择医生 | 换医生场景做最简版本 |
| AI 牙齿模拟 | 正面排齐前后对比（照片上传）、结果分享、推荐案例与医生 | LEO 现成模型服务化接入 |
| 自测问卷与报告 | 现有功能改造：弱化评分、标签化、与偏好问卷衔接 | 复用已开发页面 |
| 打卡 | 一键戴/摘、周期与副数设置、三指标评分与图表、提醒 | 不做防作弊 |
| 复诊监控 | 换套提醒（前一天 + 当天）、换套拍照上传、医生查看 | AI 对比留到第二步，后台人工 |
| 内容（发现） | 小红书式信息流、图文/视频帖子、医生案例模板、医生主页、基础过滤 | 视频自托管；推荐先按规则 |
| 消息 | 私信 1:1、评论、系统通知、微信订阅消息 | |
| 商城 | 有赞类 SaaS 接入，小程序内展示与下单 | 不上正畸类产品 |
| 保持器订单 | 需求登记 → 口扫（线下）→ 供应商设计（跳转）→ 确认 → 生产 → 物流 → 复购提醒 | 供应商 webhook 回传状态 |
| 找医生 | 列表、基础筛选、医生主页 | 找机构/找产品第二步 |
| 增长 | 医生二维码、患者邀请码（挂靠医生）、基础积分 | 奖励目录第二步 |
| 医生端 | 小程序角色：我的患者、数据看板（打卡、换套）、发布内容、私信、方案跳转 | 网页端第二步 |
| 运营后台 | 内容审核、用户/医生管理与认证、消息模板、订单查看、基础数据 | 最小可用 |
| 合规 | 协议与授权文本、AI 免责、未成年人提示、禁用词检查 | |

### 1.3 里程碑

| 时间 | 里程碑 |
| --- | --- |
| 2026-09 下旬 | 架构与技术选型冻结；IA 与页面清单确认；小程序主体申请提交；LEO 回国期间线下对齐 |
| 2026-10 | 平台骨架可跑（登录、角色、绑定、内容流、后台）；AI 模拟插件接通 |
| 2026-11 | 打卡、复诊监控、私信、商城接入完成；保持器订单流程与供应商联调；内容团队开始灌入内容 |
| 2026-12 | 内测：医生先进（目标每位医生建案例，累计 100–1000 个案例）→ 医生邀请患者（每人约 10 个）；年底灰度上线 |
| 2027-01 → 03 | 真实保持器订单验证；修复与打磨；积分与推荐规则上线；准备第二步 |

### 1.4 依赖与风险

- 公司主体、域名、证书、二类器械销售经营范围：不到位则无法正式发布与开通支付。
- 供应商设计软件的接入方式（跳转 / web-view）与回传接口，需在 10 月前谈定。
- 内容储备：上线前需要足够的官方科普与医生案例，否则信息流空壳。
- 团队仅两名开发加一名设计，范围必须守住「粗版可用」，不追求每个模块精致。
- 微信平台政策：医疗类目、内容安全、web-view 业务域名需提前核对。

## 2. 第二步：保持器 + 轻微微调（2027-04 → 2027-12）

### 2.1 目标

- 在保持器链路稳定的基础上，开放轻微反弹微调（Mini/Standard/Pro 套餐），形成第二条现金流。
- 方案设计与专家审核流程产品化；复诊监控由人工走向 AI 对比。
- 通过服务套餐把患者留在保持期之后。
- 医生网页端上线，服务患者多、有团队的医生。

### 2.2 产品范围

| 模块 | 第二步交付内容 |
| --- | --- |
| 微调订单 | 套餐选择、适合度初筛（规则 + 口扫）、方案设计、专家审核、分副生产与发货、佩戴监控 |
| 方案设计 | 供应商软件深度整合或 web-view 内嵌；专家端在流程内；方案回传结构化数据（副数、周期） |
| 复诊监控 | AI 对比（脱套、不贴合、进度偏离标签）、医生处理工作台、异常推送 |
| AI 模拟 | 侧貌模拟（VTO，医生工具优先）、贴面（DSD）与美白模拟并入同一入口 |
| 内容与推荐 | 多维推荐算法（偏好问卷 + 浏览行为）、互助板块、话题/标签体系、医生排名 |
| 服务套餐 | 保持无忧 / 牙周护理 / 家庭套餐；年付；支付宝周期扣款；签约门诊履约 |
| 找机构 / 找产品 | 机构主页与评价、四类产品预设与品牌露出 |
| 增长 | 奖励目录、优惠券（门诊提供）、医生积分排名与广告位 |
| 医生网页端 | 团队协作、报表、批量患者管理、方案评审 |
| 口扫与数据 | STL/PLY 建档、反弹对比基线、自研封牙/分割模块服务化 |
| 商城 | 与打卡联动（美白剂）、复购推荐 |

### 2.3 里程碑

| 时间 | 里程碑 |
| --- | --- |
| 2027 Q2 | 微调订单流程与专家审核上线；侧貌模拟内测；服务套餐首个 SKU |
| 2027 Q3 | 复诊监控 AI 对比上线；推荐算法上线；医生网页端上线 |
| 2027 Q4 | 找机构/找产品上线；医生排名与广告位；自研设计模块替换首个供应商环节；月活达到阶段目标 |

### 2.4 依赖与风险

- 微调涉及医疗边界：必须保持「AI 初筛 + 医生审核 + 合规生产 + 佩戴监控」路径，宣传不承诺疗效。
- 专家团队人力与响应时效决定订单周期。
- 套餐履约依赖签约门诊网络。
- 自研模块替换要有回退方案，不影响在途订单。

## 3. 第三步：完整正畸平台（2028 起）

### 3.1 目标

- 隐形矫治全流程在平台闭环：医生拍照模拟 → 交流 → 选套餐 → 签约 → 定金 → 下单 → 分副发货 → 打卡与监控 → 保持期 → 套餐。
- 自有 OEM 矫治器成为主要收入，目标价 200 元/副，主攻三四五线城市。
- 四端协同：门诊品牌露出、供应商产品曝光、广告位与导流商业化。
- 关键技术自研化：排牙/设计模块替换供应商，形成自有 IP。
- 视需要推出 App（iOS 优先），承接更重的医生工具与推送。

### 3.2 产品范围

| 模块 | 第三步交付内容 |
| --- | --- |
| 隐形矫治订单 | 全流程、分副发货与更换计划、重启机制、按步收费 |
| 方案设计 | 自研排牙/设计模块（LEO 现有排牙与分割能力产品化）、多方案对比、患者偏好驱动的方案推荐 |
| 医生成长 | 全科医生操作培训内容、专家支持常态化、案例激励 |
| 商业化 | 广告位售卖、信息流广告、导流佣金、B 端订单系统（诊所白牌） |
| 四端 | 门诊端页面与数据、供应商端曝光与订单对接 |
| 增长 | 线上投流承接页、多平台矩阵内容、区域推广工具 |
| App | iOS 优先的 App 版本（复用 uni-app 工程），推送与相机能力增强 |
| 数据 | 口扫、照片、佩戴、方案数据沉淀，训练自有模型 |

### 3.3 里程碑（粗略）

| 时间 | 里程碑 |
| --- | --- |
| 2028 H1 | 隐形矫治订单上线；自研设计模块承担部分订单；门诊端上线 |
| 2028 H2 | 广告与导流商业化；区域医生网络；App 版本 |

### 3.4 依赖与风险

- 矫治器生产资质与供应链掌控（自产或深度绑定代工）。
- 医疗合规与互联网医疗政策边界。
- 自研设计模块的成熟度与医生接受度。
- 资金与团队扩张节奏。

---

## 4. 贯穿三步的固定原则

1. 一个小程序、两种角色，医生高级功能走网页，不做第二套 App（App 版仅作为同一工程的编译目标）。
2. 核心数据（用户、疗程、照片、口扫、订单）永远在自己系统内；AI、设计、商城、视频、支付以插件接入，可替换。
3. 每一步先跑通一条收钱的链路，再扩模块。
4. 灰度顺序：医生 → 医生案例 → 医生邀请患者 → 患者裂变。
5. 月度与杨老师对齐一次，周会推进；范围变更由 PM 统一进入需求池。
