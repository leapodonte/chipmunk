# Smilelab DSO 开发演示容量与运行边界

采样日期：2026-10-05。这里记录实际短样本及已配置上限，不把并发连接数解释为同时在线用户容量。

## 主机与服务

VPS 为 8 vCPU、23,458 MiB 内存、193 GiB 系统盘。02:33 UTC 采样：可用内存 20,911 MiB，使用约2,547 MiB，磁盘可用87 GiB；交换分区已有约1,763 MiB占用，不能仅凭当前可用内存认定过去从未内存紧张。主机还承载 CAD、分割、Git/Forgejo、门户与 CI runner。

| Smilelab 服务 | CPU 配额 | 内存上限 | 升级前空闲采样 |
|---|---:|---:|---:|
| 平台 API 与工作台 | 1 | 512 MiB | 56.75 MiB |
| 平台 PostgreSQL | 0.5 | 512 MiB | 41.99 MiB |
| Odoo | 2 | 3 GiB | 337.3 MiB |
| Odoo PostgreSQL | 0.5 | 512 MiB | 163.4 MiB |

四服务合计4.5 GiB上限、4个CPU配额；这些是限额，不是预留。当前空闲约600 MiB支持轻量开发与演示，有明显内存余量。实际瓶颈更可能先是平台单CPU、数据库半CPU或共享构建争抢；GitHub自托管runner目前没有CPU/内存限制，重型构建可影响演示。新DSO CI使用托管runner；本次没有擅自重启或调整既有runner。

平台业务池最多15连接，限流使用独立5连接；平台数据库max_connections为40。限流按用户及登录来源实施，失败业务事务也不能撤销限流计数。不能简单把40连接换算成40用户。

## 独立栈短样本

`tools/benchmark-dso.py` 只接受隔离测试交付文件中的localhost地址，读取上下文、患者目录、CRM线索和运维摘要，不写真实患者数据。合成小数据集、暖缓存、HTTP loopback，没有TLS或公网延迟。测试 API 限1CPU/512MiB，PostgreSQL限0.5CPU/256MiB；每阶段200请求，轮换四个员工账号，同账号请求可能串行于事务锁。

| 并发请求 | 完成请求 | 请求/秒 | p50 | p95 | p99 | 失败 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 200 | 111.9 | 8.3 ms | 11.5 ms | 17.9 ms | 0 |
| 5 | 200 | 109.9 | 15.6 ms | 96.5 ms | 182.4 ms | 0 |
| 20 | 200 | 77.1 | 189.4 ms | 602.7 ms | 779.7 ms | 0 |

该结果支持少量开发者和演示操作的使用，尚未覆盖长时间峰值、生产规模数据、集中媒体上传、大量病历、Odoo财务报表或真实AI/GPU。上线前需以实际业务操作比例、目标数据量和公网路径测试，并定义响应时间与错误率目标；不能将短样本作为生产用户数量承诺。

## 磁盘与备份预算

私有媒体每文件10MiB、每患者100MiB，上传前要求至少10GiB磁盘余量。每日快照保留约7天，包含两库、两文件卷、源码和秘密；约87GiB当前余量必须同时承担Docker镜像、构建缓存、Git历史及快照增长。保留7份全量媒体快照时，10GiB原始媒体可能额外需要约70GiB快照空间，图片通常压缩收益有限。需监控磁盘并配置异地备份/保留方案，再允许持续大批量媒体导入。

当前备份在同一VPS，无PITR或离站副本。部署前保存完整快照，更新失败时按对应数据库、源码、文件及镜像版本一起恢复。正式患者数据的保留与删除规则尚未确定。
