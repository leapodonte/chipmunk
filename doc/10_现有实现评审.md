## 0. 评审方法与边界

逐文件通读了全部 C# 源码、配置、Docker 与 nginx 文件。对几处依赖框架行为的判断，直接查了 FreeSql 与 FreeRedis 的源码而不是凭印象。

**本机没有 .NET SDK，也没有 PostgreSQL，所以没有编译、没有跑 `--init`、没有发请求。** 下文每条阻塞性缺陷都附了验证方法，请在有环境的机器上过一遍再定。凡是我无法百分之百确定的，都标了「需验证」。

## 1. 总体评价

这是一套从上一个项目继承来的通用后台脚手架：账号、角色、模块权限、企业、系统配置，加一个微信小程序静默登录的雏形。三层分层清楚，响应包、异常、签名、会话、本地化、CodeFirst 建表这些横切机制都已经有了，作为起点是够用的。

但它**还没有一行牙齿矫正的业务代码**，而且带着一批从旧项目继承的缺陷和残留。其中两条会让小程序端在第一天就跑不起来：`user` 表的唯一索引写错了字段名导致只能注册一个用户，`AppCheck` 过滤器用了后台的会话服务导致所有需要登录的小程序接口都拿不到会话。这两条不修，阶段 0 的「小程序可登录」交付物无法达成。

一句话：**骨架可用，血肉未生，先修再建。**

## 2. 架构与分层

### 2.1 现状

```
Admin.Api        控制器（admin/ 6 个，app/ 1 个）、过滤器 3 个、会话服务 2 个、日志、扩展方法
   ↓ 只依赖
Admin.Services   业务服务 9 个、DTO 11 组、CodeException、EncryptorService、WechatService、本地化资源
   ↓ 只依赖
Admin.Models     FreeSql 实体 11 个、FreeSqlExtension（建库）
   ↓
PostgreSQL（单库 admin）    Redis（会话、微信 token）
```

依赖方向正确，Services 不引用 Web 宿主，DTO 集中在 Services 层供两边共用。这是值得保持的。

### 2.2 请求管线

```
自定义中间件：注入 HttpHeaders 配置项 → OPTIONS 直接 200
UseAuthorization（无认证方案，实际空转）
MapControllers
  ├─ AdminCheck / AppCheck 过滤器：签名校验 → 会话校验 → 放入 HttpContext.Items
  ├─ 控制器：GetRequestAsync<T>() 读体、反序列化、DataAnnotations 校验
  └─ AdminResponse 过滤器：捕获异常转 Response<T>、打印请求与响应日志
```

缺的东西：没有健康检查端点，没有 OpenAPI，没有限流，没有全局异常中间件（异常只在过滤器层处理，过滤器之外的异常会裸露），没有 `IHttpClientFactory`，没有定时任务框架，没有任何测试项目。

### 2.3 双模式入口

`Program.cs` 顶层语句，`--init` 时 CodeFirst 同步表结构并写种子，否则启动 Web。思路简洁，但 `--init` 有一个操作性风险，见 §3 P0-4。

## 3. 必须在阶段 0 修复的缺陷

按严重程度排序。每条给出证据位置、后果、修法、验证方法。

### P0-1 `user` 表两个唯一索引字段名写错，导致只能注册一个用户

**证据**
[User.cs:47](../api/Admin.Models/User.cs:47) 与 [User.cs:48](../api/Admin.Models/User.cs:48) 声明索引字段为 `open_id` 与 `unique_id`，而实体属性是 [User.cs:88](../api/Admin.Models/User.cs:88) 的 `openid` 与 [User.cs:93](../api/Admin.Models/User.cs:93) 的 `unionid`。`Program.cs` 没有配置命名转换，列名就是属性名。

**机制**
FreeSql 解析 `[Index]` 时对每个字段先按属性名查 `ColumnsByCs`，再按列名查 `Columns`，都查不到就**静默跳过该字段**，一个都匹配不上才跳过整个索引。源码在 `FreeSql/Internal/UtilsExpressionTree.cs` 的 `AuditTableInfo` 方法。于是：

| 索引 | 声明 | 实际建出来的 |
| --- | --- | --- |
| `user_idx_1` | `name, deleted_at` 唯一 | `name, deleted_at` 唯一，正常 |
| `user_idx_2` | `open_id, deleted_at` 唯一 | **`deleted_at` 单列唯一** |
| `user_idx_3` | `unique_id, deleted_at` 唯一 | **`deleted_at` 单列唯一** |

所有未删除用户的 `deleted_at` 都是 0。第一个微信用户能插入，第二个就撞 `user_idx_2` 的唯一约束，`wx-mp-login` 抛异常返回 500。

**后果**：小程序只能有一个用户。这是阶段 0「小程序可登录」交付物的直接阻塞。因为 `--init` 不报错，问题要到第二个人登录时才暴露。

**修法**：把两处字段名改为 `openid` 与 `unionid`。同时建议给 `--init` 加一步自检：同步完成后查询 `pg_indexes`，把每个实体声明的索引列与实际建出的列逐一比对，不一致就打印告警，把这类静默跳过变成可见错误。

**验证**：执行 `--init` 后运行

```sql
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'user';
```

若看到 `user_idx_2` 的定义只含 `deleted_at`，即确认。

### P0-2 `AppCheck` 用了后台会话服务，所有需登录的小程序接口不可用

**证据**：[AppCheckAttribute.cs:85](../api/Admin.Api/Filters/AppCheckAttribute.cs:85) 取的是 `AdminSessionService`。小程序会话由 `AppSessionService` 写在 `app:sessions:` 前缀下，后台服务去 `admin:sessions:` 前缀读，永远读不到，且反序列化目标类型也是 `AdminSession`。

**后果**：除白名单里的 `wx-mp-login` 外，任何小程序接口都会返回 401。`CLAUDE.md` 已记为已知问题，但它是阻塞项，不是待办项。

**修法**：改为 `AppSessionService`；`HttpContext.Items["session"]` 存 `AppSession`；给 [ControllerBaseExtensions.cs:13](../api/Admin.Api/Utils/ControllerBaseExtensions.cs:13) 增加 `GetAppSession()`，现有 `GetSession()` 只返回 `AdminSession`，小程序控制器没法用。

**验证**：登录拿到 `session_id` 后，带 `App-Session` 头调任意一个需登录的小程序接口。

### P0-3 登录时全表更新 `updated_at`

**证据**：[AccountService.cs:52](../api/Admin.Services/AccountService.cs:52) 的 `Update<Account>().Set(...).ExecuteAffrowsAsync()` 没有 `Where`；[UserService.cs:58](../api/Admin.Services/UserService.cs:58) 同样。

**后果**：每次后台登录把 `account` 表所有行的 `updated_at` 改掉；每次微信登录把 `user` 表所有行改掉。用户量上来后每次登录都是一次全表写，锁与 IO 都会出问题，而且 `updated_at` 从此失去意义。

**修法**：补 `.Where(a => a.id == acc.id)` 与 `.Where(a => a.id == user.id)`。

**验证**：两个账号，登录其中一个，查另一个的 `updated_at` 是否被改。

### P0-4 每次 `--init` 都把 admin 密码重置回 `Admin@12345`

**证据**：[SystemService.cs:97](../api/Admin.Services/SystemService.cs:97) 生成固定密码，[SystemService.cs:100](../api/Admin.Services/SystemService.cs:100) 用 `InsertOrUpdate` 无条件覆盖。对比 `InitSystemOptions` 用了 `IfExistsDoNothing`，两处处理不一致。

**后果**：`CLAUDE.md` 的「新表检查清单」要求每加一张表就运行 `--init` 同步结构。生产上每次这么做，管理员密码都会被重置，且 `system.changed_pwd` 标记不会被清，导致后台不再提示改密。这是一个必然会踩的运维陷阱。

**修法**：admin 账号只在不存在时插入，存在则不动。表结构同步与种子数据分成两个命令，比如 `--sync` 与 `--seed`。

### P0-5 软删除只有字段没有实现

**证据**：[AccountService.cs:203](../api/Admin.Services/AccountService.cs:203)、[CorpService.cs:122](../api/Admin.Services/CorpService.cs:122)、`RoleService.Delete` 全部是物理删除；全库没有任何一处查询带 `deleted_at == 0` 条件；`UserService.WxMpLoginAsync` 按 `openid` 查用户时也不排除已删除行。

**后果**：`CLAUDE.md` 与开发计划都把软删除当作既定约定，唯一索引也按软删除设计（把 `deleted_at` 放进索引），但代码里它并不存在。后续业务表如果照抄现状，会一半软删一半硬删。

**修法**：二选一并写进 `CLAUDE.md`。要么真做软删除：删除改为写 `deleted_at`，所有查询加过滤，FreeSql 支持全局过滤器 `fsql.GlobalFilter.Apply<ISoftDelete>("soft", a => a.deleted_at == 0)`，一处配置全库生效。要么放弃软删除，去掉三处 `deleted_at` 列和索引里的 `deleted_at`。不要停在现在这个中间态。

### P0-6 两个接口没有路由特性，无法按预期访问

**证据**：[CorpController.cs:68](../api/Admin.Api/Controllers/Admin/CorpController.cs:68) 的 `GetAsync` 与 [AuthController.cs:86](../api/Admin.Api/Controllers/Admin/AuthController.cs:86) 的 `CurrentUserRolesAsync` 没有 `[HttpPost("...")]`。

**后果**：在 `[ApiController]` 加属性路由的控制器里，无路由特性的公共方法会落到控制器根路径且不限方法，`admin/corp` 与 `admin/auth` 会被这两个方法占用或产生歧义。前端按 `admin/corp/get` 调用会 404。

**修法**：分别加 `[HttpPost("get")]` 与 `[HttpPost("current-user-roles")]`。

### P0-7 微信 access_token 缓存三处错，外加关闭了 TLS 校验

**证据**
- [WechatService.cs:198](../api/Admin.Services/WechatService.cs:198)：`Math.Min(0, rsp.expires_in - 300)` 永远小于等于 0。FreeRedis 对小于 1 秒的过期时间不发 `EX`，key 永不过期。应为 `Math.Max`。
- [WechatService.cs:189](../api/Admin.Services/WechatService.cs:189) 读 `KEY_AccessToken + userId`，[WechatService.cs:199](../api/Admin.Services/WechatService.cs:199) 写 `KEY_AccessToken`，键不一致，缓存永远不命中。`userId` 参数对小程序级 token 本身没有意义。
- [WechatService.cs:32](../api/Admin.Services/WechatService.cs:32)：`ServerCertificateCustomValidationCallback = delegate { return true; }` 对微信接口关闭了证书校验，中间人可以伪造 `jscode2session` 响应返回任意 `openid`，等于绕过登录。
- [WechatService.cs:195](../api/Admin.Services/WechatService.cs:195) 与 [WechatService.cs:205](../api/Admin.Services/WechatService.cs:205) 每次调用新建 `HttpClient`，高并发下 socket 耗尽。

**后果**：现阶段只用到 `jscode2session`，token 缓存的错还没触发；一旦订阅消息推送上线（阶段 2）就会每次推送都去微信取 token，触发频控。证书校验关闭是安全问题，与是否触发无关。

**修法**：`Math.Max`；统一键名并去掉 `userId`；删除证书回调；`WechatClient` 改为通过 `IHttpClientFactory` 注入的具名客户端。

### P0-8 本地化资源键不存在

**证据**：[AuthController.cs:61](../api/Admin.Api/Controllers/Admin/AuthController.cs:61)、L77、L91、L109 用 `_localizer["InvalidStream"]`，资源文件里只有 `InvalidSession`。[Module.cs:72](../api/Admin.Services/DTO/Module.cs:72) 的 `ModuleReorderRequest` 引用 `CannoValid_CannotEmptytEmpty`，是拼写事故。

**后果**：前者返回给前端的错误文案是字面量 `InvalidStream`；后者一旦启用该 DTO，校验时抛异常。资源文件里还残留 `Name1`、`Color1`、`Bitmap1`、`Icon1` 四个模板键。

### P0-9 示例配置的 Redis 连接串带空格，照抄会连不上

**证据**：`api/Admin.Api/appsettings.example.json` 与 `docker/api/opt/appsettings.example.json` 都写成 `"127.0.0.1: 6379,..."`。FreeRedis 的 `ConnectionStringBuilder.Parse` 只对整段做 `Trim`，不处理 `host:port` 中间的空格，`Host` 会变成 `127.0.0.1: 6379`。

**修法**：去掉空格。真实的 `appsettings.json` 被 gitignore，可能已经是对的，但示例文件是新人唯一的模板。

### P0-10 两份示例配置数据库名不一致

`api/Admin.Api/appsettings.example.json` 是 `Database=admin`，`docker/api/opt/appsettings.example.json` 是 `Database=smilecheck`。前者是当前项目，后者是旧项目残留。统一为 `admin` 或改成项目名。

## 4. 安全

### 4.1 四把密钥硬编码在源码

[EncryptorService.cs:15](../api/Admin.Services/EncryptorService.cs:15) 到 L30 四个 `const`。其中 `RequestKey` 同时出现在前身仓库小程序的 `sign.ts` 和 `tools/smoke.mjs` 里，等于已经公开。`ServerPwdKey` 泄露则所有密码哈希可离线破解。

建议：全部移入配置，生产用环境变量注入；`RequestKey` 接受它是防误用而非防伪造的事实，安全边界放在会话与限流上。

### 4.2 密码哈希没有盐、没有慢函数

`EncodePassword = HMAC(HMAC(pwd, ClientKey), ServerKey)`。同一密码在所有账号上得到同一哈希，没有逐用户盐；HMAC-SHA256 每秒可算上亿次，无法抵抗离线穷举。后台账号数量少，但它们是最高权限。

建议：服务端换成 PBKDF2 或 Argon2id 加逐用户随机盐，`Account.password` 存算法标识、盐、哈希。客户端那层 HMAC 可以保留作为传输混淆。

### 4.3 RBAC 只算权限不查权限

`ModuleService` 把账号的模块与动作算得很细并放进 `AdminSession.modules`，但**没有任何一个后台接口检查它**。任何能登录后台的账号都能调 `admin/account/add`、`admin/role/set-modules`、`admin/module/update`。角色权限目前只影响前端菜单显示。

建议：加一个 `[RequireModule("account","edit")]` 之类的特性，在过滤器里对照 `session.modules` 校验；这是平台后台上线前的硬要求。

### 4.4 签名 15 分钟内可重放

签名覆盖 `body + timestamp`，容差 ±15 分钟（[AdminCheckAttribute.cs:72](../api/Admin.Api/Filters/AdminCheckAttribute.cs:72)），`RequestId` 只是原样回显，没有去重。抓到一个签名请求可以在 15 分钟内重放。对写接口（加账号、改密码、打卡）这是实际风险。

建议：`RequestId` 作为 nonce 写 Redis，15 分钟内重复即拒绝；容差收窄到 5 分钟。

### 4.5 日志打印全部请求头与请求体

[AdminResponseAttribute.cs:89](../api/Admin.Api/Filters/AdminResponseAttribute.cs:89) 逐个打印请求头，包括 `Admin-Session` 与 `App-Session`；请求体原样打印，登录接口的密码哈希、以后的手机号、openid 都会进日志。`LogService` 级别是 `Level.All`。同时 [AdminResponseAttribute.cs:57](../api/Admin.Api/Filters/AdminResponseAttribute.cs:57) 把包括 401、402 在内的所有异常按 Error 记录，正常的会话过期会刷屏。

建议：请求日志只在 Development 开启，会话与密码类字段脱敏，`CodeException` 记 Warn 不记 Error。

### 4.6 其余

| 项 | 位置 | 说明 |
| --- | --- | --- |
| nginx 允许 TLS 1.0 与 1.1 | `docker/nginx/opt/nginx.conf` | 改为 `TLSv1.2 TLSv1.3` |
| 登录接口没有限流 | `AuthController`、`UserController` | 后台登录可无限尝试；加 IP 与账号维度限流 |
| Docker 镜像源 | `docker/docker/daemon.json` | 四个镜像源里三个是来路不明的第三方，供应链风险，只留阿里云 |

## 5. 数据层

### 5.1 约定与实现脱节

| 约定 | 实现情况 |
| --- | --- |
| `updated_at` 每次更新维护 | 只有 `CorpService.UpdateAsync` 做了；`AccountService`、`RoleService`、`ModuleService` 的更新都不动它 |
| 软删除 | 见 P0-5，未实现 |
| 唯一索引附带 `deleted_at` | 依赖软删除成立，目前是空中楼阁 |
| JSON 列 | [Module.cs:55](../api/Admin.Models/Module.cs:55) 用 `jsonb`，[AccountModule.cs:46](../api/Admin.Models/AccountModule.cs:46) 与 `RoleModule` 用 `json`，同一类数据两种类型 |

### 5.2 两套 JSON 库混用

实体里的 `actions` 是 Newtonsoft 的 `JArray`（配合 FreeSql JsonMap），而接口层用 `System.Text.Json` 反序列化请求体。`admin/module/update` 的请求 DTO `ModuleUpdateRequest.modules` 是 `List<Module>`，`System.Text.Json` 不认识 `JArray`，`actions` 字段会得到空或错误值。需验证：发一个带 `actions` 的 `module/update` 请求，查库看是否写成 `[]`。

建议：DTO 里用 `string[]` 或 `HashSet<string>`，进服务层再转 `JArray`，实体类型不要出现在请求 DTO 中。

### 5.3 可空标注矛盾

[CorpAccount.cs:73](../api/Admin.Models/CorpAccount.cs:73) 与 L79 的 `nickname`、`avatar` 标了 `IsNullable = false` 但类型是 `string?`，插入 null 会被数据库拒绝。`department_id` 是 `required Guid?`，`required` 与可空并存，语义不清。

### 5.4 分页与查询

`page_size` 没有上限，客户端可以传 100 万。`ListAsync` 里 `q.OrderByDescending(...)` 没有回赋值，FreeSql 的查询对象是就地修改并返回自身，所以能工作，但换任何一个不可变风格的库都是 bug，建议统一写成 `q = q.OrderBy...`。

`SetSource` 更新是全列覆盖，`admin/module/update` 允许前端提交整个 `Module` 对象，包括 `id` 与 `visible`，缺少字段级白名单。

### 5.5 建议增加的自检

`--init` 结束后自动做三件事并打印：每张表实际建出的索引与声明对比；每张表的列与实体对比；种子数据行数。FreeSql 静默跳过的行为决定了这一步不能省。

## 6. 运行时与运维

| 项 | 位置 | 问题 | 建议 |
| --- | --- | --- | --- |
| 同步等异步 | [AdminCheckAttribute.cs:64](../api/Admin.Api/Filters/AdminCheckAttribute.cs:64) 与 `AppCheck`、`AdminResponse` 的 `.Result` | 高并发下线程池饥饿 | 改用 `IAsyncActionFilter` |
| 请求体读三次 | 过滤器验签、控制器解析、响应过滤器打日志 | 有 `EnableBuffering` 所以能工作，但每次重读 | 验签时读一次放进 `Items` 复用 |
| 默认文化 en-US | [Program.cs:65](../api/Admin.Api/Program.cs:65) | 与需求相反 | 改 zh-Hans，已在开发计划 |
| `UseAuthorization` 空转 | [Program.cs:149](../api/Admin.Api/Program.cs:149) | 没有认证方案，纯装饰 | 删除或接入真正的策略 |

## 8. 值得保留的设计

评审不能只挑毛病。以下几点是对的，后续业务代码应当延续：

1. 三层分层与依赖方向。
2. `Response<T>` 加 `CodeException` 的统一错误模型，前端只需看 `code`。
3. `Request.Validate()` 把 DataAnnotations 校验集中在一处，DTO 上的资源化错误消息为双语打好了底。
4. 模块加动作的 RBAC 数据模型，粒度合适，只差服务端强制。
5. `Guid.Empty` 作为系统管理员哨兵值，并在更新、删除、改角色处都做了保护。
6. `--init` 单命令建库建表写种子，新人上手成本低。
7. 签名加时间戳的防篡改机制，方向对，只需补 nonce。
8. Redis 滑动会话。
9. 用属性名做列名的小写风格与 Unix 秒时间列，简单一致。
