### 3.3 软删除与唯一索引的写法差异

两边都做软删除，但唯一约束的实现不同，这一点容易踩坑。

本仓库：`[Index("user_idx_2", "open_id ASC,deleted_at ASC", IsUnique = true)]`，把 `deleted_at` 放进唯一索引。未删除行的 `deleted_at` 为 0，删除时写入时间戳，于是同一个 `open_id` 可以有一行有效加多行已删除。

迁入的 `07`：`CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`，用 PostgreSQL 的部分索引。

两种都能达到「未删除行唯一」的效果。仓库的写法不依赖部分索引，将来换 MySQL 也成立；部分索引的语义更直白。**新表沿用仓库写法**，不要混用。

## 4. 数据模型对照

这是冲突最集中的部分。`07_数据库设计_DDL_V1.sql` **不能直接执行**，原因有三：主键类型是 Guid 不是 ULID，时间列是 Unix 秒不是时间戳，建表要走 FreeSql CodeFirst 而不是 SQL 脚本。

### 4.1 表的对应关系

| 业务 | 迁入 `07` 的表 | 本仓库开发计划的表 | 说明 |
| --- | --- | --- | --- |
| 账号 | `identity.app_user` + `identity.user_role` | `user`（加 `role` 列） | 仓库用一列区分角色，迁入文档用独立的多角色表 |
| 医生 | `identity.doctor_profile` + `doctor_verification` | `doctor`（1:1 档案，含认证状态） | 概念一致，仓库把认证状态并进档案表 |
| 机构 | `identity.clinic` | `corp` + `corp_photo` + `corp_review` | 仓库已有 `corp` 系列实体，更完整 |
| **疗程** | `identity.course` + `course_event` | **无对应概念** | 见 4.2，这是最需要决策的一处 |
| 打卡 | `care.wear_period` / `checkin_event` / `wear_score` | `aligner_plan` / `checkin_record` / `wear_stat` | 概念一一对应，仅命名不同 |
| 复诊 | `care.change_task` / `monitor_photo` | `replace_plan` / `replace_record` | 同上 |
| 内容 | `content.post` / `post_media` / `post_comment` / `reaction` / `follow` / `topic` / `post_topic` | `post` / `post_media` / `comment` / `follow` | 仓库无话题与点赞收藏表 |
| 医生案例 | `content.case_detail`（帖子的扩展表） | `doctor_case`（独立表） | 建模思路不同 |
| 积分 | `growth` schema，0 张表 | `points_account` / `points_ledger` | 仓库已规划，迁入文档只留了空 schema |
| 商城 | `trade` schema，0 张表 | `mall_product` / `cart_item` | 同上 |
| 找产品 | 无 | `brand` / `product` / `product_ref` | 迁入文档漏了这个模块的建模 |
| 首页 | `ops.banner` | `banner` / `news` | 仓库多了新闻动态 |
| AI | `ai.plugin_registry` / `ai_task` / `ai_result` / `plugin_usage` | `ai_task` / `ai_material` / `ai_report` | 见 4.3 |
| 文件 | `ops.file_object` | 未单独建表，落 `file_key` | 见 4.4 |
| 配置协议审计 | `ops.app_config` / `agreement` / `user_agreement_accept` / `audit_log` / `sms_log` | `SystemOption`，其余未规划 | 迁入文档在合规留证上更完整 |

### 4.2 疗程这个概念要不要保留

`identity.course` 是 9 月 7 日会议明确的结论：疗程是医患关系的唯一单位，医患多对多，换医生等于结束当前疗程另开一条，历史数据保留。

本仓库没有这个概念。医患关系隐含在 `aligner_plan` 里，而 `aligner_plan` 是矫治计划，一个患者可能有多个，但没有表达「这段治疗归哪个医生」。

**要决策**：如果不引入疗程，以下场景没有落点。

1. 患者换医生后，历史打卡与复诊记录归属谁。
2. 医生看板上「我的患者」如何界定，是看 `aligner_plan` 还是看绑定关系。
3. 二维码绑定后、尚未开始矫治时，医患关系存在哪里。
4. 同一患者先后被两个医生服务时，私信会话挂在哪一层。

建议：在 `aligner_plan` 之上补一张关系表，或给 `aligner_plan` 加 `doctor_id` 并接受「一次矫治计划即一段医患关系」的简化。前者贴合会议结论，后者实现更省。这条不定，打卡与复诊模块的归属查询写不出来。

### 4.3 AI 模块的建模差异

迁入文档的 `ai.plugin_registry` 是一张插件注册表，把 AI 能力、供应商设计软件、商城都抽象成可开关可灰度可替换的插件，业务代码按 capability 路由，不认具体供应商。这来自 9 月 7 日「平台是整合者」的结论。

本仓库的开发计划把 AI 当作单一外部系统，用 `ai_task` / `ai_material` / `ai_report` 三张表打通「上传—任务—回调—展示」，没有注册表和路由层。

两者不矛盾，是详略之别。**建议**：本期按仓库的三张表实现，够用；但把 `ai_task` 上的 `plugin_id` 或 `provider` 列留出来，将来接第二家 AI 供应商时不用改表。迁入文档 `05` §7 的三类插件契约（异步任务、跳转加回调、基础设施封装）仍然值得作为对外接口的模板，尤其是回调验签与幂等那部分。

### 4.4 文件账本

迁入文档的 `08` §8.2 提出一个问题：文件与业务之间不要同时存在三套关联机制。本仓库的方案是只落 `file_key` 字符串，没有文件账本表。

这个方案本身是自洽的，只有一套机制，比迁入文档描述的状况干净。但要注意两点：

1. 没有账本就无法反查孤儿文件。本地磁盘阶段问题不大，切 OSS 后要么补账本，要么接受存储里有垃圾。
2. `file_key` 如果在多张业务表里重复出现，删除业务行时不知道文件还有没有别的引用。

**建议**：先按仓库方案做，但在文件签发接口里记一张最小的登记表（key、业务类型、业务 id、大小、创建时间），成本很低，将来切 OSS 与做清理都要用。

## 5. API 契约对照

迁入文档 `05` §6 列了 M1 的完整接口清单，写作时假设的路由是 `/app`、`/admin`、`/doctor`、`/open`。本仓库实际是 `app/[controller]` 与 `admin/[controller]`，没有 `/api` 前缀，`doctor` 与 `open` 两组尚不存在。

**处理方式**：接口清单的**业务语义**仍然有效，可以直接用作控制器与动作的规划；但路径、请求头、错误码要按 `CLAUDE.md` 的约定改写。三处必改：

1. 路由改为 `app/[controller]` 形式。
2. 请求头补 `App-RequestId`；签名容差按 ±15 分钟。
3. 错误码表要与 `CodeException` 的既有取值对齐，签名不符是 402，不是迁入文档里的 401。

`/open` 这组（插件回调与 webhook）本仓库还没有，但开发计划 5.1 说 AI 要「对外提供回调接口，沿用签名鉴权」，语义相同，建立时可参考迁入文档 `05` §7.2 的回调协议，重点是验签、幂等、以及回调丢失时的兜底轮询。

## 6. 两根时间轴不要混

迁入文档里有两套阶段划分，加上本仓库的一套，一共三根轴，很容易串。

| 轴 | 出处 | 划分 | 时间跨度 |
| --- | --- | --- | --- |
| 业务三步走 | 迁入 `02` | 保持器切入 → 保持器加微调 → 正畸平台 | 2026-09 到 2028 以后 |
| 开发里程碑 | 迁入 `04` | M0 到 M4 | 2026-09 到 2027-03 |
| 分期开发计划 | 本仓库 `开发计划1.0.md` | 阶段 0 到阶段 5，加后期专项 | 未标注日期 |

本仓库的阶段划分与迁入 `04` 的 M0 到 M4 **不是同一套**，模块顺序也不同。仓库按「账号 → 找机构医生产品 → 打卡复诊 → 资讯积分 → 商城 → AI」推进，迁入文档按「骨架 → 依从性沟通 → 交易供应链 → 灰度」推进。

**建议以仓库的阶段划分为准**，它更贴近当前代码状态。迁入 `04` 的价值在于两点：一是 14 项外部插件的清单与降级策略，二是每项工作的负责人与前置依赖，这两部分可以嫁接到仓库的阶段里。

迁入 `02` 的三步走是业务口径，不与开发阶段一一对应，不要拿它排开发。
